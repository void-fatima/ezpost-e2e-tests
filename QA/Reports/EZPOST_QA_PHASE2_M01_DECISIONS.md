- سه anchor خانه: `/#products` برای بخش بسته‌ها، `/#how-it-works` برای فرایند، `/#contact` برای تماس. L01/L02 وجود و نمونهٔ ورود را ثبت کرده‌اند؛ تأیید کامل خوانایی/جای‌گیری نهایی نداریم.
- LOGIN-RETURN: لینک ثبت‌شدهٔ «بازگشت به فروشگاه» از `/login` به `/` است. پیشنهاد حفظ ROOT به‌عنوان انتظار؛ انتخاب SHOP تصمیم تغییر رفتار است.
- RECOVERY: در خطای محصول ناموجود، کنترل ثبت‌شده button با متن «بازگشت به فروشگاه» است. L06 رسیدن به ROOT و محتوای خانه را ثبت کرده؛ پیشنهاد ROOT برای هر دو کیس N07 است.
- TRUST پیشنهادی برای baseline اولیه، همان URL ثبت‌شده است:

```text
https://trustseal.enamad.ir/?id=8080557&Code=iQSgAIZTBHxXc01FzMx9C4KFkoRxjUTt
```

تصویب TRUST فقط مقایسهٔ مقصد اولیهٔ لینک را پوشش می‌دهد؛ تعلق id/Code به تاجر و اعتبار نشان همچنان موضوع N06-TC04 است. query به‌صورت scheme/host/path/key/value مقایسه می‌شود، نه ترتیب نوشتاری پارامترها.

برای N07-TC04، دنبالهٔ مورد انتظار دقیقاً پس از بازیابی و با entryهای جدید ساخته می‌شود: ROOT→PRODUCT→MISSING؛ Back به PRODUCT/ROOT و Forward به PRODUCT/MISSING. این پیشنهاد، سیاست push/replace خودِ کنترل بازیابی را تعیین نمی‌کند. L07 قابلیت این روش در مرورگر بررسی قبلی را نشان می‌دهد؛ اثبات قابلیت runner آینده هنوز یک کار فنی است.

**P-VIS — پیشنهاد مشترک و محدود:** نتیجهٔ ناوبری با مسیر مصوب و هویت main سنجیده شود؛ برای anchor، بخش متناظر پس از پایان جابه‌جایی قابل مشاهده/خواندن باشد؛ برای کیبورد، focus کنترل قابل تشخیص باشد؛ برای TOP، header/hero دوباره قابل مشاهده شود. انتقال اجباری focus به heading، scroll دقیق صفر، مدت animation، متن دائمی heading یا conformance کامل پیشنهاد نشده است. DOM و مشاهدهٔ انسانی جدا گزارش شوند. سقف انتظار محدود و روش تشخیص پایان رندر باید پیش از اجرا توسط QA در محیط runner ثبت شود؛ اعداد تشخیصی ۱۰/۳۰ ثانیه و scrollهای قبلی الزام محصول نیستند.

## ۴. چهار اصلاح قبل/بعد — مشروط به تصمیم مقصد

H01/H02 مقصد قدیمی را ثابت می‌کنند، نه اینکه آن مقصد هنوز الزام انتشار باشد.

## ۶. مسیر خروجی مرورگر: بررسی فنی و اقدام لازم

برای بررسی تنظیم مسیر از راهنمای `playwright-cli` و README نصب موجود Playwright MCP استفاده شد؛ هیچ نصب یا فراخوانی ابزار مرورگری صورت نگرفت. یافته‌های محلی این مرحله:

- تنظیم اتصال موجود در بخش `[mcp_servers.playwright]` شامل `--browser chrome` است و `--output-dir` ندارد. دو پردازش سرور MCP مشاهده‌شده نیز فقط این گزینه را نشان می‌دهند؛ معلوم نیست کدام پردازش اتصال ابزار این گفتگو است. نبود flag اثبات نبود env override در پردازش‌ها نیست.
- دو artifact از ساعت ۱۹:۲۵ UTC در `EZPost/.playwright-mcp/` وجود دارد؛ محتوایشان مربوط به WordPress است، نه EZPost. این مرحله آنها را تغییر نداد و به شواهد QA اضافه نکرد. وجودشان فقط نشان می‌دهد زمانی خروجی در ریشهٔ Desktop نوشته شده؛ اثبات root مؤثر اتصال فعلی یا انحصاری‌بودن خروجی EZPost نیست.
- طبق README نصب موجود، `--output-dir` مسیر فایل‌های خودکار را تعیین می‌کند؛ نام صریح فایل همچنان نسبت به workspace root تفسیر می‌شود. گزینهٔ `--ignore-roots` root را از current working directory می‌گیرد. بنابراین تغییر output-dir به‌تنهایی مشکل root فایل‌های صریح را حل نمی‌کند.

**نتیجهٔ فعلی: root مؤثر اتصال موجود قابل تأیید نیست و مسیر اختصاصی زیر QA/Evidence پیکربندی صریح ندارد.** ابزارهای در دسترس، فرمان تغییر root/rebind اتصال جاری ندارند. اتصال موجود در این جلسه اصلاح یا با یک probe مرورگری امتحان نشد؛ برای جلوگیری از هر خروجی خودکار احتمالی در Tapin، ابزار مرورگر فراخوانی نشد. این پیش‌نیاز فنی مانع تصمیم‌گیری مستندی نیست.

مسیر اختصاصی تعیین‌شده برای اتصال آینده:

```text
C:\Users\LOCAL_USER\Desktop\EZPost\QA\Evidence\M01-Browser
```

اقدام دقیق بعدی برای مسئول محیط/QA، بدون دست‌کاری تنظیم عمومی یا اتصال Tapin:

1. یک اتصال MCP **مختص پروژه EZPost** در میزبان ابزار تعریف و همان اتصال انتخاب شود؛ اتصال مشترک فعلی تغییر نکند. working directory آن دقیقاً Desktop EZPost باشد.
2. با همان نصب موجود، executable برابر `C:\Program Files\nodejs\node.exe` و آرگومان‌های زیر تنظیم شود؛ این snippet دستور پیشنهادی است و اینجا اجرا نشده است:

```json
[
  "C:\\Users\\LOCAL_USER\\AppData\\Local\\npm-cache\\_npx\\9833c18b2d85bc59\\node_modules\\@playwright\\mcp\\cli.js",
  "--browser", "chrome",
  "--isolated",
  "--ignore-roots",
  "--output-dir", "C:\\Users\\LOCAL_USER\\Desktop\\EZPost\\QA\\Evidence\\M01-Browser"
]
```

3. فقط اتصال EZPost بازراه‌اندازی شود. `--ignore-roots` فقط وقتی معتبر است که میزبان، cwd موردنظر را واقعاً اعمال کند. اگر میزبان cwd یا اتصال جدا نمی‌پذیرد، قابلیت مرورگر تا اصلاح میزبان در تعویق بماند؛ به config عمومی یا Tapin رجوعِ تغییردهنده نشود.
4. قبل از هر اتصال به برنامه، در context ایزوله با `about:blank` یک artifact خودکار و یک فایل صریح زیر مسیر تعیین‌شده تولید و مسیر خروجی/اجازهٔ root با ابزار فایل بررسی شود. خروجی خودکار هم باید در `M01-Browser` باشد؛ موفقیت فقط فایل صریح کافی نیست. این probe در مرحلهٔ فعلی انجام نشده است.
5. تا موفقیت هر دو کنترل، ناوبری برنامه و تولید evidence مرورگری متوقف بماند. نصب جدید، تغییر global env، اجرای npx با دانلود یا بستن نشست/تب نامرتبط لازم نیست.

این کار یک مسئلهٔ فنی با روش مشخص است؛ از مالک محصول سؤال نمی‌شود که root چگونه تنظیم شود. فقط در صورت تغییر نصب موجود باید مسیر CLI دوباره از نصب محلیِ در دسترس پیدا شود.

در صورت رد تعویق N06-TC04، N08-TC04 یا N09-TC01، اطلاعات موردنیاز دقیقاً همان رکورد تاجر، قواعد سه ردیف نقش/سبد یا manifest مخاطب/محتوا در جدول ۱۸تایی است؛ پرسش جدید یا بازکشف دادهٔ موجود لازم نیست. برای N06-TC02/TC03 و N05-TC03، کمبود اصلی قابلیت/شاهد فنی است و QA باید آن را فراهم کند.

**پس از این تصمیم‌ها، اقدام بعدی فقط در صورت درخواست شما اصلاح سند مرجع با همان ۳۰ ID و ثبت baseline/دامنهٔ مصوب است.** مجوز پیاده‌سازی و سپس اجرای تست جدا هستند. در این مرحله فقط این سند تصمیم ساخته شد؛ M02، Cypress، نصب، Git، تغییر دادهٔ برنامه و تغییر فایل‌های Tapin انجام نشد.

کنترل نهایی این بسته: حضور دقیق ۱۸ ID مسدود و والدهایشان، تطابق نقل‌های قبل با فایل اصلی، جمع ۵+۴+۹ و ۱۹+۲+۹، اعتبار لینک‌های محلی و یکسان‌ماندن SHA-256 تمام ۲۹ فایل قبلی زیر QA بررسی شد. وضعیت‌های مرجع ۱۰/۱/۱/۱۸ و `NOT EXECUTED` حفظ شدند.
