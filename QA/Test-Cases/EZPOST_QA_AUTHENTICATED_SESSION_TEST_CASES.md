# قراردادهای ورود دستی و بررسی نشست عادی EZPost

تاریخ طراحی و به‌روزرسانی اجرا: ۱۷ نوامبر ۲۰۲۶. شاخهٔ درخواستی این batch: `test/authenticated-session`؛ workspace مستقل Desktop EZPost. این سند، قرارداد پیش از code و نتیجهٔ واقعیِ اجرای همان subset را جدا نگه می‌دارد؛ cases/report قبلی authentication، نتایج عمومی۱۸PASS، IDهای M01/ordering/cart و failureهای تاریخی تغییر نمی‌کنند. **وضعیت اولیهٔ زمان طراحی تمام ردیف‌های تازه NOT EXECUTED بود**؛ وضعیت فعلی بر اساس شواهد زیر ثبت شده است.

## checkpoint اجرای واقعی

`AUTH-SESSION01` در Cypress نمایان، با ورود دستی شماره/OTP توسط خود کاربر و assertionهای خودکار پس از آن، روی یک source ثابت در Chrome و Firefox اجرا شد. این **یک journey در هر مرورگر** است؛ `AS-*` تست‌های مستقل اضافه نیستند. controlled/mock authentication در این اجرا صفر بود.

کاربر اکنون صریحاً **ایجاد حساب عادی از مسیر معمول OTP برای شمارهٔ تعیین‌شده و نگه‌داشتن حساب** را مجاز کرده است. این steering، محدودیت existing-only مرحلهٔ قبلی را برای همین هویت و همین مسیر جایگزین می‌کند؛ «موجودبودن حساب تأیید نشده» دیگر blocker blanket احراز هویت این batch نیست. هیچ مجوزی برای admin، هویت دوم، account deletion، profile/address/customer writes، order یا payment ایجاد نشده است. account retention انتخاب کاربر است؛ reset یا حذف حساب برای completion این batch درخواست یا اجرا نمی‌شود.

شماره و سپس OTP را **خود کاربر مستقیماً در Cypress نمایان** وارد می‌کند. این بخش MANUAL-ASSISTED SETUP است؛ به‌تنهایی هیچ testcase خودکار challenge/OTP را PASS نمی‌کند. فقط assertionهای هویت، ordinary-role، UI و continuity که واقعاً اجرا شده‌اند می‌توانند automated نتیجه داشته باشند. این مسیر ممکن است حساب قبلی را وارد کند یا حساب جدید بسازد؛ بدون شاهد مستقلِ واقعی، «حساب تازه ساخته شد» ادعا نمی‌شود.

## پیش‌شرط و contract مشترک قبل از پیاده‌سازی

1. مرورگر اختصاصی Cypress و همان پروژه/وابستگی‌های موجود؛ ابتدا session واقعی `user:null` و **guest cart واقعاً خالی** احراز شود. علاوه بر UI خالی، منبع واقعی guest sync در localStorage با کلید مشاهده‌شدهٔ `ezpost_guest_cart_v1` باید absent یا آرایهٔ خالی باشد؛ این شرط read-only در preflight و دوباره پیش از هر start/verify بررسی می‌شود. پس خالی‌بودن موقت SSR به‌تنهایی prerequisite را تأیید نمی‌کند. جریان عادی client پس از login، guest sync دارد؛ طبق C1 سبد مهمان خالی، cart write نمی‌سازد. اگر مهمان از ابتدا قلم یا state نامعلوم داشت، توقف prerequisite و عدم clear/add/edit لازم است؛ POST cart-items مجاز نمی‌شود. بدون personal/admin session، copied cookies، auth bypass یا تزریق state موفق؛ user در همین context شماره/OTP را وارد کند.
2. شمارهٔ **واقعاً submitشده**، پیش از دریافت session موفق، فقط در حافظهٔ خصوصی همان setup به‌عنوان identity anchor گرفته شود. مقدار آن در خروجی ابزار، console، assertion message، screenshot/video، fixture، config، file یا Git ذخیره نشود. OTP فقط داخل حافظهٔ خصوصی browser برای تطبیق شش input واقعاً submitشده با همان request بررسی می‌شود؛ به خروجی ابزار یا گزارش صادر، چاپ یا persist نمی‌شود. Cypress نمایان می‌تواند دادهٔ زندهٔ کاربر را در حافظه و UI همان context داشته باشد؛ raw command/network log و DOM/screenshot آن نباید export شود. assertionهای حساس فقط boolean با پیام بی‌مقدار دارند.
3. مقایسهٔ identity باید شمارهٔ session واقعی را با همین anchor مستقل تطبیق دهد؛ comparison دو API با هم یا `user !== null` کافی نیست. قواعد normalization موردنیاز برای همین شماره باید از قرارداد واقعی frontend/server کشف شوند؛ equivalence همهٔ digitها، prefixها یا formatها از این یک نمونه نتیجه‌گیری نشود. اگر normalization قابل اتکا مشخص نشد، mismatch/insufficient evidence روشن ثبت شود و مقدار مورد انتظار از session کپی نشود.
4. فقط **POST دقیق** `/api/v1/auth/otp/start` با payload کلید `mobile` و `/api/v1/auth/otp/verify` با کلیدهای `mobile/code`، طبق C1، به‌عنوان مجوز تازه در slice جدا permit شوند؛ هرکدام حداکثر یک درخواست در هر browser و فقط در phase درست با input/request واقعاً منطبق. broad `/api/v1/auth/**` یا wildcard mutation اجازه نمی‌گیرد. استثنای read-only موجودِ POST quote محصول، با همان scope guard پایه حفظ می‌شود؛ cart بعد ورود ممکن است آن را خودکار بخواند و این اجازهٔ cart write نیست. shape واقعی و هویت خصوصی با اقدام user correlate شوند؛ هیچ مقدار payload عمومی ذخیره نشود. هویت دیگر، resend/retry نامحدود، shipping/order/cart-items و mutationهای دیگر fail-closed بمانند. guard suiteهای قدیمی عوض نشود. GETهای واقعی `/api/v1/auth/session` و `/api/v1/auth/me` فقط برای observation مشروع‌اند و body/header/cookie آن‌ها persist نشود.
5. اجازهٔ این دو مسیر، موفقیتشان را ثابت نمی‌کند. درخواست واقعی با اقدام کاربر و مرحلهٔ challenge/verify correlate شود، ولی هیچ request-count/HTTP200/toast جای identity+role+UI oracle را نگیرد. path literals H3 به‌تنهایی response schema یا backend authorization proof نیستند.
6. ordinary-role بر اساس C1 مقدار واقعی `customer` و label «مشتری» دارد؛ این literal حدسی نیست. `/auth/session` و `/auth/me` باید role همین ordinary reference را بدهند و account UI با همان session سازگار باشد؛ `admin/print/warehouse` نباید ordinary PASS شوند. اگر runtime schema با C1 ناسازگار بود همان failure/prerequisite روشن حفظ شود، نه اینکه role assertion conditional حذف شود. account link یا نبود لینک admin به‌تنهایی role proof نیست.
7. ورود موفق می‌تواند به route یا صفحهٔ تکمیل اطلاعات برود؛ مقصد واقعی observation می‌شود. تا تصویب return policy، هیچ `next`/fallback/checkout مقصد اجباری حدس زده نمی‌شود. اگر فرم customer/profile/address ظاهر شد، فقط inspection بدون submit؛ حتی اگر برای ادامه required باشد در همین مرز متوقف شود.

| AS-CUSTOMER-OBS01 | **READ-ONLY NAVIGATION ATTEMPT COMPLETED / FORM NOT OBSERVED** در هر دو مرورگر | direct checkout خواندنی امتحان شد؛ settled مقصد `/cart` و فرم customer مشاهده نشد. validation/persistence/customer-form coverage اجرا نشده و PASS ندارد؛ این شاهد policy مصوب empty-cart نیست |

N1 و شواهد checkpoint اجرای واقعی، مرجع این وضعیت‌ها هستند؛ هیچ‌یک outcomeهای تاریخی عمومی۱۸PASS یا failureهای قبلی را جایگزین نمی‌کند.

support hook و spec از getter مشترکِ `authenticated-session-runtime.js` برای همان gate ابزار Cypress استفاده می‌کنند؛ این اشتراک فقط در harness است و state موفق به AUT تزریق نمی‌کند. closureهای خصوصی anchor/session در status عمومی قرار نمی‌گیرند. نتایج cart در این journey به observation ساختار و حفظ snapshot همان اقلام محدودند؛ برابری snapshot، صحت مستقل محصول/بسته/quantity، merge policy یا قیمت را تأیید نمی‌کند.

| شناسهٔ observation / نگاشت | پیش‌شرط و اقدام | oracle و خروجی مجاز | آنچه پوشش نمی‌دهد / وضعیت اولیهٔ زمان طراحی |
|---|---|---|---|
| AS-CART-OBS01 → T04، AUTH-07/A09 | session مشروع همین user؛ لینک/route cart واقعی و مجاز؛ فقط مشاهده، بدون add/edit/remove/reset/cleanup | وجود/تعداد و ساختار کنترل‌های cart فقط به‌صورت sanitized inventory؛ identity/session anchored قبل/بعد navigation حفظ و guardِ صفر mutation رعایت شود. دادهٔ قبلی user دست‌نخورده بماند؛ اگر values یا custom content شخصی است وارد evidence عمومی نشود | **READ-ONLY OBSERVATION / NOT EXECUTED**؛ cart فعلی ممکن است خالی یا پُر باشد. empty فرض نشود؛ مشاهدهٔ بعد login، merge/retention صحیح یا price correctness را ثابت نمی‌کند و test cart-integrity PASS نام نمی‌گیرد |

در این batch، account retained است و دادهٔ قبلی نیز حفظ می‌شود؛ cleanup حذف حساب/سبد/اطلاعات مشتری لازم یا مجاز فرض نمی‌شود. هیچ خط قدیمی cart با ownership نامعلوم تغییر نمی‌کند. اگر navigation لازم درخواست غیرمجاز ساخت، guard آن را متوقف و observation همان‌جا incomplete ثبت می‌کند؛ برای ادامه guard ضعیف نمی‌شود.

## ثبت نتیجه، correctness و privacy

برای هر critical test بازبینی دوم بپرسد: «اگر identity، role یا state ادعاشده خراب باشد، آیا هنوز پاس می‌شود؟» oracleهای بالا باید wrong identity، role نادرست، session مهمان، UI قدیمی و continuity شکسته را رد کنند؛ این review امکان همهٔ false positiveها را منتفی نمی‌کند. اگر assertion روی property غایب conditional skip شد یا expected identity از همان response برداشته شد، claim مربوط معتبر نیست.

اجرای واقعی در `cypress open → E2E → Chrome` سپس Firefox، روی همان source/test/helper نسخهٔ ثابت انجام شد. source hash و application-opened/spec-loaded/tests-completed در شاهد هر مرورگر جدا ثبت‌اند؛ manual setup، automated checks، controlled simulation و observation جدا نگه داشته شدند. تمام ردیف‌های این سند **در زمان طراحی اولیه NOT EXECUTED بودند**؛ نتیجهٔ فعلی محدود به checkpoint اجرا و جدول وضعیت فعلی بالاست. هر failure/attempt/rerun باید جدا با شواهد سانیتایزشده حفظ شود. هیچ mock موفق authentication یا cookie/session fabrication مجاز یا استفاده نشده است.

هیچ شماره، OTP، raw authenticated response، header/cookie/token، account identifier، personal screenshot یا browser profile به PUBLIC نمی‌رود. مقدارهای خصوصی فقط در حافظهٔ لازم برای assertion بوده و پس از استفاده/پایان context آزاد شوند؛ account خود طبق خواست user باقی می‌ماند. evidence عمومی فقط booleanها، نوع claim و outcome سانیتایزشده دارد. P10 و سایر نتایج تاریخی باز باقی می‌مانند؛ این مرحله E2E کامل سفارش/پرداخت نیست.
